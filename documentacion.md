# Avianto: documentación de implementación <!-- Última modificación: 2026-10-26 -->
## Alcance y arquitectura <!-- Última modificación: 2026-10-26 -->
Avianto es una aplicación web para la operación de un taller de motos. El frontend Next.js presenta las pantallas de trabajo y administración; el backend Java 21 con Spring Boot 3 expone la API bajo `/api`; PostgreSQL conserva los datos y Flyway administra el esquema. <!-- Última modificación: 2026-10-26 -->
El proxy público Caddy enruta `/api/*`, `/actuator`, `/swagger-ui` y `/v3/api-docs` al contenedor `avianto-api` en el puerto interno 8081; el resto del tráfico va al frontend. PostgreSQL no se publica fuera de la red interna de Docker. El bloque de Avianto está reflejado en `ops/avianto.caddy` y la pila local usa reglas equivalentes en `ops/nginx.conf`. <!-- Última modificación: 2026-10-26 -->
La API es JSON salvo exportaciones XLSX, descarga de PDF e imágenes de fichas. Los identificadores persistidos son UUID; las fechas de API usan UTC y los reportes presentan fechas en `America/Argentina/Buenos_Aires`. <!-- Última modificación: 2026-10-26 -->
## Rutas y contratos API <!-- Última modificación: 2026-10-26 -->
La autenticación usa `POST /api/auth/login` con usuario/email y contraseña; devuelve tokens de acceso y renovación junto con el usuario. `POST /api/auth/refresh` rota la sesión, `POST /api/auth/logout` revoca el token y `GET /api/auth/me` devuelve el usuario autenticado. <!-- Última modificación: 2026-10-26 -->
Los recursos principales se consultan y modifican bajo `/api/clientes`, `/api/motovehiculos`, `/api/perfiles`, `/api/fichas`, `/api/repuestos`, `/api/ventas`, `/api/transferencias` y `/api/services`; los listados admiten filtros, orden y paginación según el recurso. La API completa y los contratos se mantienen en `AviantoFront/docs/api-contract.md`. <!-- Última modificación: 2026-10-26 -->
Los tableros usan `/api/dashboard`, `/api/dashboard/taller`, `/api/dashboard/fichas` y `/api/dashboard/ventas`. Los reportes usan `/api/reportes/resumen` y `/api/reportes/evolucion`; la actividad administrativa se consulta en `/api/auditoria`. <!-- Última modificación: 2026-10-26 -->
La configuración usa `/api/configuracion/trabajos`, `/api/configuracion/controles`, `/api/configuracion/ventas/checklist`, `/api/configuracion/marcas-moto`, `/api/configuracion/categorias` y `/api/configuracion/usuarios`. <!-- Última modificación: 2026-10-26 -->
Los archivos se descargan desde las rutas de exportación XLSX de clientes, motos, fichas, repuestos y transferencias; el PDF de una ficha se obtiene desde `/api/fichas/{id}/pdf`. Las fotos se crean y leen desde `/api/fichas/{id}/fotos`. <!-- Última modificación: 2026-10-26 -->
Las sondas operativas son `GET /actuator/health`, `/actuator/health/liveness` y `/actuator/health/readiness`; no requieren sesión y no reemplazan los permisos de las rutas de negocio. Swagger UI está en `/swagger-ui.html` y sus recursos estáticos en `/swagger-ui/**`; ambos son el armazón público de documentación. OpenAPI (`/v3/api-docs/**`) continúa restringido a Administración. El inicializador Swagger carga `/v3/api-docs` directamente, lee `sessionStorage.avianto.session`, adjunta el JWT solo a solicitudes del mismo origen y renueva el acceso próximo a vencer. `/v3/api-docs/swagger-config` conserva su permiso exclusivo de Administración, aunque el inicializador no lo usa. <!-- Última modificación: 2026-10-26 -->
La pantalla Swagger UI se abre desde `/swagger-ui.html`; sirve para consultar el contrato OpenAPI y probar operaciones con “Try it out”. Muestra grupos, parámetros, cuerpos, respuestas y errores. El token procede de la sesión Avianto; la interfaz solo lo envía al mismo origen. Usuarios sin sesión o con rol Operario pueden cargar el armazón, pero OpenAPI responde `403` y la definición no se muestra. Los estados visibles son carga del esquema, definición disponible y error de acceso/carga. Las operaciones de la pantalla usan las rutas API documentadas en `/v3/api-docs`; la vista no agrega navegación propia a la aplicación. <!-- Última modificación: 2026-10-26 -->
## Datos y comportamiento <!-- Última modificación: 2026-10-26 -->
Flyway crea y versiona el esquema PostgreSQL. Los usuarios iniciales se crean desde variables de entorno después de las migraciones; las contraseñas se almacenan con BCrypt. <!-- Última modificación: 2026-10-26 -->
El dominio incluye clientes, motos y propietarios, fichas de taller, trabajos, controles de revisión, pedidos y pagos de repuestos, services, fichas de venta, transferencias, usuarios y auditoría. Las bajas son lógicas y conservan el historial. Los PATCH de configuración de service y controles de revisión preservan los campos omitidos; `null` o texto vacío borran solo las propiedades de texto enviadas. Las colecciones anidadas verifican la existencia de la moto y responden `404` si falta. <!-- Última modificación: 2026-10-26 -->
Las fotos de fichas se guardan como bytes en PostgreSQL con un máximo de 5 MB por imagen. Los pagos guardan idempotencia; las operaciones críticas preservan estados e historial. <!-- Última modificación: 2026-10-26 -->
El circuito de taller es `Ingresada Taller` → `Pendiente` → `En proceso` → `En revisión` → `Terminada` → `Entregada`. La revisión aprobada termina los trabajos y la entrega se registra como una acción separada. <!-- Última modificación: 2026-10-26 -->
Una moto ingresada a `Venta` queda disponible en ese circuito y obtiene una ficha de venta persistente. El presupuesto de una ficha incluye por separado sus repuestos vinculados. <!-- Última modificación: 2026-10-26 -->
## Seguridad e integraciones <!-- Última modificación: 2026-10-26 -->
Las rutas de negocio requieren JWT, excepto login, renovación, logout y health checks. Administración conserva acceso completo; Operario recibe los permisos configurados en `AVIANTO_OPERATOR_PERMISSIONS`. <!-- Última modificación: 2026-10-26 -->
Administración es necesaria para auditoría, usuarios, configuración, pagos, bajas sensibles, aprobación final, entrega y operaciones de transferencia indicadas por la API. Los endpoints vuelven a validar permisos aunque una acción no aparezca en la interfaz. <!-- Última modificación: 2026-10-26 -->
CORS permite los orígenes definidos en `CORS_ALLOWED_ORIGINS`. Swagger y OpenAPI quedan restringidos al rol Administración. Los health checks permanecen públicos; `/actuator/info` requiere sesión. Una ruta sin recurso registrado responde `404` en el formato de error JSON de Avianto. <!-- Última modificación: 2026-10-26 -->
En producción, el host `avianto.neticar.com.ar` envía rutas de negocio, Actuator y Springdoc a `avianto-api:8081`, y el resto a `avianto-web:3000`; el backend conecta con `avianto-postgres:5432` por la red privada de Docker. Las rutas del backend no cambian los permisos de Spring Security. <!-- Última modificación: 2026-10-26 -->
## Pantallas del frontend <!-- Última modificación: 2026-10-26 -->
El menú lateral y móvil navega entre Inicio, Perfiles, Wiki, Fichas, Pedidos, Services, Ventas, Transferencias, Clientes, Motos, Controles, Trabajos, Reportes, Auditoría y Administración. Los ítems de configuración y auditoría solo se muestran a Administración; el menú permite colapsar, abrir/cerrar en móvil y cerrar sesión. <!-- Última modificación: 2026-10-26 -->
### Página pública <!-- Última modificación: 2026-10-26 -->
`/` muestra la presentación de Avianto, enlaces a secciones informativas y llamadas a ingresar o contactar por WhatsApp. No consulta ni modifica la API; el enlace de ingreso abre `/login`. <!-- Última modificación: 2026-10-26 -->
### Inicio y tablero de taller <!-- Última modificación: 2026-10-26 -->
`/app` muestra el resumen operativo de Taller y Ventas; `/taller` abre el mismo tablero enfocado en Taller. Presenta motos y fichas por estado, permite agrupar por moto o ficha y abrir perfiles/fichas; el botón de ingreso abre `/ingresar`. <!-- Última modificación: 2026-10-26 -->
Consulta `GET /api/dashboard/taller`, `/api/dashboard/fichas` y `/api/dashboard/ventas`. Requiere sesión. Muestra estado de carga, error con reintento y estados vacíos para cada filtro. <!-- Última modificación: 2026-10-26 -->
### Inicio de sesión <!-- Última modificación: 2026-10-26 -->
`/login` permite autenticarse. Envía usuario/email y contraseña a `POST /api/auth/login`; al restaurar una sesión usa `/api/auth/refresh` y `GET /api/auth/me`. Una sesión válida navega a `/app`; los errores se muestran como aviso y el envío indica estado ocupado. <!-- Última modificación: 2026-10-26 -->
### Ingreso de moto <!-- Última modificación: 2026-10-26 -->
`/ingresar` y el acceso `/perfiles/nuevo` abren el formulario modal de ingreso, desde Inicio, Perfiles, Motos o Ventas. Permite buscar una moto existente o completar marca, modelo, año, kilometraje, propietario, observaciones y destino Taller/Ventas. <!-- Última modificación: 2026-10-26 -->
Consulta `GET /api/clientes/autocomplete`, `/api/configuracion/marcas-moto` y `/api/perfiles`; crea o actualiza el perfil y registra el ingreso mediante `/api/motovehiculos/{id}/ingreso`. Administración puede elegir Ventas; Operario solo puede iniciar el ingreso a Taller. La búsqueda muestra opciones vacías y el envío muestra progreso y errores. <!-- Última modificación: 2026-10-26 -->
### Perfiles <!-- Última modificación: 2026-10-26 -->
`/perfiles` lista motos con filtros por dominio, moto, cliente y estado, orden y paginación. Permite ingresar una moto, abrir su perfil, editar datos o solicitar su baja; si está en Venta permite abrir la ficha de venta. <!-- Última modificación: 2026-10-26 -->
Consulta `GET /api/perfiles`, `GET /api/dashboard/taller` y marcas para edición; modifica `/api/motovehiculos/{id}` y solicita la baja con `DELETE /api/motovehiculos/{id}`. Requiere sesión; muestra carga, error con reintento y vacío con acceso a ingreso. <!-- Última modificación: 2026-10-26 -->
### Perfil de moto <!-- Última modificación: 2026-10-26 -->
`/motos/{id}` presenta los datos principales, propietario, estado y acciones del circuito. Sus pestañas son General, Cliente, Services, Fichas, Repuestos y Venta; conserva el retorno a la lista de origen. Si el ID no existe, el backend responde `404` y la vista presenta su estado de error. <!-- Última modificación: 2026-10-26 -->
Consulta `/api/motovehiculos/{id}`, `/api/clientes/{id}`, `/api/motovehiculos/{id}/transferencias`, `/api/motovehiculos/{id}/services/historial`, `/api/fichas?motoId=...`, `/api/repuestos?motoId=...`, `/api/services/proximos` y `/api/motovehiculos/{id}/venta` según la pestaña. <!-- Última modificación: 2026-10-26 -->
Desde el perfil se puede registrar un service, cambiar configuración de mantenimiento, navegar a fichas/repuestos/venta e ingresar al circuito. La configuración envía los campos modificados a `PATCH /api/motovehiculos/{id}/config-service`: los períodos nulos no cambian y la observación vacía se envía como `null` para borrarla. Cambios de circuito requieren Administración o permiso `MOTO_CIRCUIT`; la pantalla ofrece carga, errores por panel, reintentos y vacíos por historial. <!-- Última modificación: 2026-10-26 -->
### Fichas de taller <!-- Última modificación: 2026-10-26 -->
`/fichas` lista fichas y motos ingresadas a Taller que aún no tienen ficha; filtra por búsqueda, cliente, moto, patente, estado, pago y fechas, y permite ordenar, paginar y exportar XLSX. Abre fichas y perfiles; la creación comienza desde un perfil. <!-- Última modificación: 2026-10-26 -->
Consulta `/api/fichas`, `/api/motovehiculos` para ingresos pendientes y descarga `/api/fichas/export.xlsx`. Requiere sesión; presenta carga, error con reintento y vacíos con opción de ampliar fechas. <!-- Última modificación: 2026-10-26 -->
`/fichas/nueva` crea una ficha vinculada a moto/cliente y `/fichas/{id}/editar` modifica una existente. El formulario captura fecha, datos de ingreso, trabajos, cantidades/precios, observaciones y fotos; consulta catálogo de trabajos con `/api/configuracion/trabajos/autocomplete`, crea con `POST /api/fichas` y edita con `PUT /api/fichas/{id}`. <!-- Última modificación: 2026-10-26 -->
El formulario permite agregar/quitar trabajos, cargar o quitar fotos y cancelar; protege cambios sin guardar con confirmación. Muestra progreso de guardado y errores como avisos. La API aplica permisos de estado mediante `FICHA_WRITE` cuando corresponde. <!-- Última modificación: 2026-10-26 -->
`/fichas/{id}` muestra estado, cliente, moto, trabajos, repuestos vinculados, pagos y controles de revisión; ofrece PDF, navegación a perfil/repuesto, cambios de estado, revisión y entrega según el estado y los permisos. Al editar una observación de control, el PATCH envía solo esa nota y conserva cualquier corrección necesaria omitida; `null` explícito permite borrar el texto. <!-- Última modificación: 2026-10-26 -->
Las acciones PDF y Nuevo pedido se muestran en azul Avianto sobre las cabeceras claras de sus paneles. En móvil, ambas ocupan todo el ancho disponible; los botones secundarios usan un contorno azul para distinguirse de las superficies blancas. <!-- Última modificación: 2026-10-26 -->
En móvil, los importes de trabajos y pedidos (`Subtotal trabajos`, `Total ficha`, `Total repuestos vinculados` y `Total presupuesto`) se apilan en filas independientes de ancho completo, con el total destacado en azul, igual que el balance de pagos. <!-- Última modificación: 2026-10-26 -->
En el detalle de ficha, la cabecera móvil compacta los datos de la moto y del presupuesto; las cuatro etapas principales se muestran en una sola fila, sin marcas de verificación y con el color como indicador de avance. La barra fija reúne la acción principal y “Más acciones”; los títulos de “Detalle de ficha”, “Detalle de pedidos” y “Pagos”, sus tablas y el botón PDF mantienen la identidad azul y ocupan el ancho disponible. Los datos, acciones por estado y conexión con `/api/fichas/{id}` conservan el comportamiento de escritorio. <!-- Última modificación: 2026-10-26 -->
En la tabla de trabajos, descripción, estado y precio ocupan columnas diferenciadas tanto en escritorio como en móvil; las columnas de selección/eliminación se ajustan al estado de la ficha sin superponer datos. <!-- Última modificación: 2026-10-26 -->
Consulta `/api/fichas/{id}`, `/api/fichas/{id}/repuestos`, `/api/fichas/{id}/revision` y los services de la moto. Las acciones escriben en `/api/fichas/{id}/estado`, `/trabajos/{trabajoId}`, `/revision/controles/{controlId}`, `/revision/aprobar`, `/pagos` y `/entregar`; Administración gestiona pagos, aprobación final, entrega y baja; `FICHA_WRITE` y `REVIEW_WRITE` permiten acciones de Operario configuradas. La pantalla muestra el error `404` si la ficha o la moto padre no existe. <!-- Última modificación: 2026-10-26 -->
El detalle muestra carga y error con reintento; sus paneles presentan vacíos cuando no hay trabajos, repuestos o controles. Las acciones que cierran o cancelan solicitan confirmación. <!-- Última modificación: 2026-10-26 -->

## Operación y despliegue <!-- Última modificación: 2026-10-26 -->
El backend usa `AviantoBack/Dockerfile`; el servicio API expone internamente 8081, limita memoria a 768 MB y procesos a 256 y depende del estado saludable de PostgreSQL. <!-- Última modificación: 2026-10-26 -->
Los servicios Docker Compose del backend ejecutan la API con `init: true`, para recolectar procesos hijos terminados. El healthcheck usa `CMD` directo a `wget` con timeout de 3 segundos y revisa `/actuator/health/readiness` cada 20 segundos con un límite de 5 segundos; evita una shell intermedia y procesos huérfanos. Nginx local envía Actuator y Springdoc al backend y conserva las reglas de acceso de Spring Security. <!-- Última modificación: 2026-10-26 -->
En la pila local, usar `docker compose --env-file .env -f docker-compose.yml up -d --build`; para frontend, backend, PostgreSQL y proxy, usar `docker compose --env-file .env -f docker-compose.full.yml up --build` desde `AviantoBack`. <!-- Última modificación: 2026-10-26 -->
