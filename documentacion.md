# Avianto: documentación de implementación <!-- Última modificación: 2026-10-26 -->
## Alcance y arquitectura <!-- Última modificación: 2026-10-26 -->
Avianto es una aplicación web para la operación de un taller de motos. El frontend React con Vinext presenta las pantallas de trabajo y administración; el backend Java 21 con Spring Boot 3 expone la API bajo `/api`; PostgreSQL conserva los datos y Flyway administra el esquema. <!-- Última modificación: 2026-11-18 -->
La cotización para presupuestar líneas USD se consulta bajo demanda a DolarAPI por HTTPS. La API devuelve cotizaciones de venta Oficial, Blue y MEP; una caché en memoria dura un minuto. Si la fuente no está disponible, el presupuesto en ARS sigue operativo y el formulario informa el error antes de permitir una nueva conversión USD. <!-- Última modificación: 2026-11-18 -->
El proxy público Caddy enruta `/api/*`, `/actuator`, `/swagger-ui` y `/v3/api-docs` al contenedor `avianto-api` en el puerto interno 8081; el resto del tráfico va al frontend. Spring Boot interpreta `Forwarded` y `X-Forwarded-*` mediante `server.forward-headers-strategy=framework` para generar URLs públicas HTTPS correctas. PostgreSQL no se publica fuera de la red interna de Docker. El bloque de Avianto está reflejado en `ops/avianto.caddy` y la pila local usa reglas equivalentes en `ops/nginx.conf`. <!-- Última modificación: 2026-10-26 -->
La API es JSON salvo exportaciones XLSX, descarga de PDF e imágenes de fichas. Los identificadores persistidos son UUID; las fechas de API usan UTC y los reportes presentan fechas en `America/Argentina/Buenos_Aires`. <!-- Última modificación: 2026-10-26 -->
## Rutas y contratos API <!-- Última modificación: 2026-10-26 -->
La autenticación usa `POST /api/auth/login` con usuario/email y contraseña; devuelve tokens de acceso y renovación junto con el usuario. `POST /api/auth/refresh` rota la sesión, `POST /api/auth/logout` revoca el token y `GET /api/auth/me` devuelve el usuario autenticado. <!-- Última modificación: 2026-10-26 -->
Los recursos principales se consultan y modifican bajo `/api/clientes`, `/api/motovehiculos`, `/api/perfiles`, `/api/fichas`, `/api/repuestos`, `/api/ventas`, `/api/transferencias` y `/api/services`; los listados admiten filtros, orden y paginación según el recurso. La API completa y los contratos se mantienen en `AviantoFront/docs/api-contract.md`. <!-- Última modificación: 2026-10-26 -->
Las búsquedas de texto libre de listados, filtros, autocompletados y exportaciones ignoran mayúsculas, minúsculas y acentos. El backend normaliza la consulta y compara con la extensión PostgreSQL `unaccent`; los filtros por estado, fecha e identificadores conservan su semántica tipada. <!-- Última modificación: 2026-11-13 -->
Los tableros usan `/api/dashboard`, `/api/dashboard/taller`, `/api/dashboard/fichas` y `/api/dashboard/ventas`. Los reportes usan `/api/reportes/resumen` y `/api/reportes/evolucion`; la actividad administrativa se consulta en `/api/auditoria`. <!-- Última modificación: 2026-10-26 -->
La configuración usa `/api/configuracion/trabajos`, `/api/configuracion/controles`, `/api/configuracion/ventas/checklist`, `/api/configuracion/marcas-moto`, `/api/configuracion/categorias` y `/api/configuracion/usuarios`. <!-- Última modificación: 2026-10-26 -->
Las fichas pueden consultar `/api/tipo-cambio/dolar` para las cotizaciones de venta Oficial, Blue y MEP; requiere `fichas.crear` o `fichas.editar`. `GET /api/configuracion/trabajos/sugerencias` devuelve descripciones repetidas en tres o más fichas distintas que aún no están en el catálogo y requiere `trabajos.ver`. `GET` y `PATCH /api/clientes/{id}/datos-completos` permiten consultar y completar DNI, teléfono, email, dirección y observaciones con `clientes.completar_datos`. `POST /api/fichas/{id}/trabajos/marcar-todos` completa trabajos pendientes y requiere `fichas.marcar_trabajos`; además el backend verifica que el usuario pertenezca al rol Administración. <!-- Última modificación: 2026-11-18 -->
`PUT /api/configuracion/trabajos/{id}` actualiza el precio del catálogo y admite `alcanceFichas=NO_MODIFICAR` o `FICHAS_VIGENTES`; devuelve el trabajo guardado más los conteos `fichasActualizadas` y `trabajosActualizados`. Requiere `PERM_trabajos.editar`. Las fichas futuras que seleccionen un trabajo activo toman el precio vigente del catálogo. <!-- Última modificación: 2026-11-18 -->
Los archivos se descargan desde las rutas de exportación XLSX de clientes, motos, fichas, repuestos y transferencias; el PDF de una ficha se obtiene desde `/api/fichas/{id}/pdf`. Las fotos se crean y leen desde `/api/fichas/{id}/fotos`. <!-- Última modificación: 2026-10-26 -->
Las sondas operativas son `GET /actuator/health`, `/actuator/health/liveness` y `/actuator/health/readiness`; no requieren sesión y no reemplazan los permisos de las rutas de negocio. Swagger UI está en `/swagger-ui.html` y sus recursos estáticos en `/swagger-ui/**`; ambos son el armazón público de documentación. OpenAPI (`/v3/api-docs/**`) continúa restringido a Administración. El inicializador Swagger carga `/v3/api-docs` directamente, lee `sessionStorage.avianto.session`, adjunta el JWT solo a solicitudes del mismo origen y renueva el acceso próximo a vencer. El servidor que OpenAPI anuncia respeta `X-Forwarded-Proto` y `X-Forwarded-Host` para que “Try it out” use el origen HTTPS público. `/v3/api-docs/swagger-config` conserva su permiso exclusivo de Administración, aunque el inicializador no lo usa. <!-- Última modificación: 2026-10-26 -->
La pantalla Swagger UI se abre desde `/swagger-ui.html`; sirve para consultar el contrato OpenAPI y probar operaciones con “Try it out”. Muestra grupos, parámetros, cuerpos, respuestas y errores. El token procede de la sesión Avianto; la interfaz solo lo envía al mismo origen. Usuarios sin sesión o con rol Operario pueden cargar el armazón, pero OpenAPI responde `403` y la definición no se muestra. Los estados visibles son carga del esquema, definición disponible y error de acceso/carga. Las operaciones de la pantalla usan las rutas API documentadas en `/v3/api-docs`; la vista no agrega navegación propia a la aplicación. <!-- Última modificación: 2026-10-26 -->
## Datos y comportamiento <!-- Última modificación: 2026-10-26 -->
Flyway crea y versiona el esquema PostgreSQL. Los usuarios iniciales se crean desde variables de entorno después de las migraciones; las contraseñas se almacenan con BCrypt. <!-- Última modificación: 2026-10-26 -->
El dominio incluye clientes, motos y propietarios, fichas de taller, trabajos, controles de revisión, pedidos y pagos de repuestos, services, fichas de venta, transferencias, usuarios y auditoría. Las bajas son lógicas y conservan el historial. Los trabajos de ficha guardan precio, descuento y subtotal en ARS para pagos y totales, además de moneda original, importes USD, tipo de cotización y fecha para conservar el presupuesto fuente. Los PATCH de configuración de service, controles de revisión y datos completos de cliente preservan las propiedades omitidas; una cadena vacía limpia solo el campo de texto enviado. Las colecciones anidadas verifican la existencia de la moto y responden `404` si falta. <!-- Última modificación: 2026-11-18 -->
Las fotos de fichas se guardan como bytes en PostgreSQL con un máximo de 5 MB por imagen. Los pagos guardan idempotencia; las operaciones críticas preservan estados e historial. <!-- Última modificación: 2026-10-26 -->
Al cambiar un precio del catálogo, el usuario con `trabajos.editar` puede elegir `NO_MODIFICAR` o `FICHAS_VIGENTES` (Pendiente, En proceso, En revisión y Terminada); las fichas Entregadas y Canceladas no se actualizan. Se actualizan los renglones con descripción coincidente sin distinguir mayúsculas, conservando descuentos y recalculando subtotales, total y estado de pago. Si un descuento supera el nuevo precio o el total queda por debajo de lo cobrado, toda la operación se revierte. Las fichas futuras que seleccionen un trabajo activo toman el precio vigente del catálogo. <!-- Última modificación: 2026-11-18 -->
El circuito de taller es `Ingresada Taller` → `Pendiente` → `En proceso` → `En revisión` → `Terminada` → `Entregada`. Administración puede marcar en una sola acción todos los trabajos pendientes de una ficha como realizados; se registran el usuario y la fecha de finalización, la ficha pasa a En proceso si correspondía y queda un evento agregado en auditoría. La revisión aprobada termina los trabajos y la entrega se registra como una acción separada. <!-- Última modificación: 2026-11-18 -->
Una moto ingresada a `Venta` queda disponible en ese circuito y obtiene una ficha de venta persistente. El presupuesto de una ficha incluye por separado sus repuestos vinculados. <!-- Última modificación: 2026-10-26 -->
## Seguridad e integraciones <!-- Última modificación: 2026-10-26 -->
Las rutas de negocio requieren JWT, excepto login, renovación, logout y health checks. Cada endpoint exige un permiso `PERM_<modulo.accion>` del catálogo `Permisos.java`. Los permisos vienen del rol del usuario (tabla `rol_permiso`): Administración tiene todos, y Gestión > Roles permite crear y editar el resto (secciones del menú y acciones por módulo). V39 concede `clientes.completar_datos` a todos los roles existentes; los roles nuevos lo seleccionan por defecto y puede retirarse desde permisos. `fichas.marcar_trabajos` es exclusivo del botón de Administración y vuelve a verificarse en el backend. <!-- Última modificación: 2026-11-18 -->
Administración es necesaria para auditoría, usuarios, configuración, pagos, bajas sensibles, aprobación final, entrega y operaciones de transferencia indicadas por la API. Los endpoints vuelven a validar permisos aunque una acción no aparezca en la interfaz. <!-- Última modificación: 2026-10-26 -->
CORS permite los orígenes definidos en `CORS_ALLOWED_ORIGINS`. Swagger y OpenAPI quedan restringidos al rol Administración. Los health checks permanecen públicos; `/actuator/info` requiere sesión. Una ruta sin recurso registrado responde `404` en el formato de error JSON de Avianto. <!-- Última modificación: 2026-10-26 -->
En producción, el host `avianto.neticar.com.ar` envía rutas de negocio, Actuator y Springdoc a `avianto-api:8081`, y el resto a `avianto-web:3000`; el backend conecta con `avianto-postgres:5432` por la red privada de Docker. Las rutas del backend no cambian los permisos de Spring Security. <!-- Última modificación: 2026-10-26 -->
## Pantallas del frontend <!-- Última modificación: 2026-10-26 -->
El menú lateral y móvil navega entre Inicio, Perfiles, Wiki, Fichas, Pedidos, Services, Ventas, Transferencias, Clientes, Motos, Controles, Trabajos, Reportes, Auditoría y Administración. Los ítems de configuración y auditoría solo se muestran a Administración; el menú permite colapsar, abrir/cerrar en móvil y cerrar sesión. <!-- Última modificación: 2026-10-26 -->
### Página pública <!-- Última modificación: 2026-10-26 -->
`/` muestra la presentación de Avianto, enlaces a secciones informativas y llamadas a ingresar o contactar por WhatsApp. No consulta ni modifica la API; el enlace de ingreso abre `/login`. <!-- Última modificación: 2026-10-26 -->
### Catálogo público de ventas AviantoVentas <!-- Última modificación: 2026-11-18 -->
`https://aviantomotos.neticar.com.ar/` muestra las motos destacadas, el catálogo, el proceso de revisión y el contacto. El visitante puede recorrer el carrusel, buscar por modelo, filtrar por marca, tipo, año, precio y cilindrada, ordenar por fecha, potencia, precio, año o kilometraje, alternar grilla/lista, cargar más resultados y abrir el detalle de una moto para recorrer su galería y consultar la ficha técnica; el botón de cierre aparece en la misma fila que la marca. Desde el detalle puede ir a WhatsApp o Instagram. La navegación principal enlaza Motos, Cómo trabajamos y Contacto. <!-- Última modificación: 2026-11-18 -->
La pestaña del navegador usa como favicon el isotipo SVG color de la moto en `assets/marca/isotipo-color.svg`. <!-- Última modificación: 2026-11-18 -->
Las motos con diagnóstico computarizado y banco de pruebas aprobados muestran una tilde verde “Verificada” en tarjetas y destacadas; en el detalle, el visitante puede tocarla para mostrar u ocultar la explicación. En escritorio, una barra lateral con el isotipo reemplaza la barra nativa, sigue el desplazamiento y permite arrastrar la moto o tocar la ruta para desplazarse; en dispositivos táctiles se mantiene la barra del sistema. <!-- Última modificación: 2026-11-18 -->
La pantalla es pública y no requiere sesión ni permisos. En el despliegue actual `apiBase` es nulo: `src/core/api.js` resuelve los datos desde `src/core/data.js` y no consulta ni modifica endpoints de AviantoBack. El detalle muestra el estado de carga de la ficha; si los filtros no encuentran resultados, aparece “No hay motos con estos filtros”. No hay estado de error de red ni reintento porque la versión publicada usa datos locales y no realiza solicitudes API. Los datos de contacto aún contienen valores de ejemplo. <!-- Última modificación: 2026-11-18 -->
### Inicio y tablero de taller <!-- Última modificación: 2026-10-26 -->
`/app` muestra el resumen operativo de Taller y Ventas; `/taller` abre el mismo tablero enfocado en Taller. Presenta motos y fichas por estado, permite agrupar por moto o ficha y abrir perfiles/fichas; el botón de ingreso abre `/ingresar`. <!-- Última modificación: 2026-10-26 -->
Consulta `GET /api/dashboard/taller`, `/api/dashboard/fichas` y `/api/dashboard/ventas`. Requiere sesión. Muestra estado de carga, error con reintento y estados vacíos para cada filtro. <!-- Última modificación: 2026-10-26 -->
### Inicio de sesión <!-- Última modificación: 2026-10-26 -->
`/login` permite autenticarse. Envía usuario/email y contraseña a `POST /api/auth/login`; al restaurar una sesión usa `/api/auth/refresh` y `GET /api/auth/me`. Una sesión válida navega a `/app`; los errores se muestran como aviso y el envío indica estado ocupado. <!-- Última modificación: 2026-10-26 -->
### Ingreso de moto <!-- Última modificación: 2026-10-26 -->
`/ingresar` y el acceso `/perfiles/nuevo` abren el formulario modal de ingreso, desde Inicio, Perfiles, Motos o Ventas. Permite buscar una moto existente o completar marca, modelo, año, kilometraje, propietario, observaciones y destino Taller/Ventas. <!-- Última modificación: 2026-10-26 -->
Consulta `GET /api/clientes/autocomplete`, `/api/configuracion/marcas-moto` y `/api/perfiles`; crea o actualiza el perfil y registra el ingreso mediante `/api/motovehiculos/{id}/ingreso`. Administración puede elegir Ventas; Operario solo puede iniciar el ingreso a Taller. La búsqueda de dominio y el autocompletado de cliente ignoran mayúsculas y acentos; muestran opciones vacías y el envío indica progreso y errores. <!-- Última modificación: 2026-11-13 -->
### Perfiles <!-- Última modificación: 2026-10-26 -->
`/perfiles` lista motos con filtros por dominio, moto, cliente y estado, orden y paginación. Los filtros de texto por dominio, moto y cliente ignoran mayúsculas y acentos. Permite ingresar una moto, abrir su perfil, editar datos o solicitar su baja; si está en Venta permite abrir la ficha de venta. <!-- Última modificación: 2026-11-13 -->
Consulta `GET /api/perfiles`, `GET /api/dashboard/taller` y marcas para edición; modifica `/api/motovehiculos/{id}` y solicita la baja con `DELETE /api/motovehiculos/{id}`. Requiere sesión; muestra carga, error con reintento y vacío con acceso a ingreso. <!-- Última modificación: 2026-10-26 -->
### Perfil de moto <!-- Última modificación: 2026-10-26 -->
`/motos/{id}` presenta los datos principales, propietario, estado y acciones del circuito. Sus pestañas son General, Cliente, Services, Fichas, Repuestos y Venta; la pestaña seleccionada tiene esquinas cuadradas y conserva el retorno a la lista de origen. Si el ID no existe, el backend responde `404` y la vista presenta su estado de error. <!-- Última modificación: 2026-11-18 -->
Consulta `/api/motovehiculos/{id}`, `/api/clientes/{id}`, `/api/motovehiculos/{id}/transferencias`, `/api/motovehiculos/{id}/services/historial`, `/api/fichas?motoId=...`, `/api/repuestos?motoId=...`, `/api/services/proximos` y `/api/motovehiculos/{id}/venta` según la pestaña. En el encabezado, “Editar perfil” requiere `motos.editar` y modifica el registro con `PUT /api/motovehiculos/{id}` en un modal, sin abandonar la pantalla. Si también tiene `marcas.ver`, consulta `/api/configuracion/marcas-moto` para seleccionar marcas; de lo contrario conserva la marca actual. El guardado muestra progreso; los errores de catálogo o validación se notifican y permiten corregir o reintentar. <!-- Última modificación: 2026-11-18 -->
La pestaña “Clientes” muestra nombre y DNI en celdas contiguas de la primera fila, y teléfono y dirección en la segunda, divididos por la cuadrícula. Con `clientes.ver` y `clientes.editar`, “Editar cliente” abre el formulario completo sobre `/motos/{id}` y modifica `/api/clientes/{id}` con `PUT`; incluye email y observaciones, y si el cliente aún no está cargado consulta `GET /api/clientes/{id}` antes de abrirlo. Si el usuario tiene `clientes.completar_datos` y no cuenta con ambos permisos de edición completa, “Completar datos” abre el formulario acotado y usa `GET/PATCH /api/clientes/{id}/datos-completos`. Ambas acciones mantienen el perfil abierto; la carga y los errores de guardado se informan en el diálogo o mediante notificaciones. <!-- Última modificación: 2026-11-18 -->
Desde el perfil se puede registrar un service, cambiar configuración de mantenimiento, navegar a fichas/repuestos/venta e ingresar al circuito. La configuración envía los campos modificados a `PATCH /api/motovehiculos/{id}/config-service`: los períodos nulos no cambian y la observación vacía se envía como `null` para borrarla. Cambios de circuito requieren Administración o permiso `MOTO_CIRCUIT`; la pantalla ofrece carga, errores por panel, reintentos y vacíos por historial. <!-- Última modificación: 2026-10-26 -->
### Fichas de taller <!-- Última modificación: 2026-10-26 -->
`/fichas` lista fichas y motos ingresadas a Taller que aún no tienen ficha; filtra por búsqueda, cliente, moto, patente, estado, pago y fechas, y permite ordenar, paginar y exportar XLSX. La búsqueda de ficha, cliente y patente ignora mayúsculas y acentos. Abre fichas y perfiles; la creación comienza desde un perfil. <!-- Última modificación: 2026-11-13 -->
Consulta `/api/fichas`, `/api/motovehiculos` para ingresos pendientes y descarga `/api/fichas/export.xlsx`. Requiere sesión; presenta carga, error con reintento y vacíos con opción de ampliar fechas. <!-- Última modificación: 2026-10-26 -->
`/fichas/nueva` crea una ficha vinculada a moto/cliente y `/fichas/{id}/editar` modifica una existente. El formulario captura fecha, datos de ingreso, trabajos, cantidades/precios, observaciones y fotos; consulta catálogo de trabajos con `/api/configuracion/trabajos/autocomplete`, cuya búsqueda ignora mayúsculas y acentos, crea con `POST /api/fichas` y edita con `PUT /api/fichas/{id}`. <!-- Última modificación: 2026-11-13 -->
En alta y edición, cada renglón de trabajo permite elegir ARS o USD. El selector de cotización de venta (Oficial, Blue o MEP) muestra fuente y hora de actualización; las líneas USD guardan importe original, tipo/cotización usada y fecha, y muestran el equivalente ARS. El total, IVA, pagos y catálogo permanecen en ARS. Las líneas USD existentes conservan su cotización al editar. La pantalla consulta `GET /api/tipo-cambio/dolar` con permiso `fichas.crear` o `fichas.editar`; durante la carga informa progreso, y ante error permite reintentar, mantiene el uso en ARS y deshabilita la selección USD para nuevas líneas. <!-- Última modificación: 2026-11-18 -->
Al seleccionar un trabajo del catálogo, el formulario toma su precio vigente como sugerencia. Las fichas existentes conservan sus precios salvo que Administración los propague desde Trabajos. El ingreso futuro no está permitido; las fichas que se creen luego del cambio usarán el precio actualizado. <!-- Última modificación: 2026-11-13 -->
El formulario permite agregar/quitar trabajos, cargar o quitar fotos y cancelar; protege cambios sin guardar con confirmación. Muestra progreso de guardado y errores como avisos. La API aplica permisos de estado mediante `FICHA_WRITE` cuando corresponde. <!-- Última modificación: 2026-10-26 -->
`/fichas/{id}` muestra estado, cliente, moto, trabajos, repuestos vinculados, pagos y controles de revisión; ofrece PDF, navegación a perfil/repuesto, cambios de estado, revisión y entrega según el estado y los permisos. Al editar una observación de control, el PATCH envía solo esa nota y conserva cualquier corrección necesaria omitida; `null` explícito permite borrar el texto. <!-- Última modificación: 2026-10-26 -->
En la tabla de trabajos, cada renglón con observación muestra una luz circular azul de marca junto a su descripción y conserva el texto desplegado; la animación es breve y queda estática con `prefers-reduced-motion`. Administración con `fichas.marcar_trabajos` ve “Marcar todos realizados” cuando hay trabajos pendientes; confirma la cantidad antes de enviar `POST /api/fichas/{id}/trabajos/marcar-todos` y la pantalla muestra progreso, error o la ficha actualizada. <!-- Última modificación: 2026-11-18 -->
Quienes tienen `clientes.completar_datos` ven el panel “Datos del cliente” en `/fichas/{id}` con DNI, teléfono, email, dirección y observaciones. El panel usa `GET /api/clientes/{clienteId}/datos-completos`; “Completar datos” o “Editar datos” abre el formulario y guarda con `PATCH` en esa misma ruta. Carga, error con reintento y campos sin completar son estados explícitos; el permiso permite esta tarea aunque el usuario no tenga `clientes.ver` o `clientes.editar`. <!-- Última modificación: 2026-11-18 -->
Las acciones PDF y Nuevo pedido se muestran en azul Avianto sobre las cabeceras claras de sus paneles. En móvil, ambas ocupan todo el ancho disponible; los botones secundarios usan un contorno azul para distinguirse de las superficies blancas. <!-- Última modificación: 2026-10-26 -->
En móvil, los importes de trabajos y pedidos (`Subtotal trabajos`, `Total ficha`, `Total repuestos vinculados` y `Total presupuesto`) se apilan en filas independientes de ancho completo, con el total destacado en azul, igual que el balance de pagos. <!-- Última modificación: 2026-10-26 -->
En el detalle de ficha, la cabecera móvil compacta los datos de la moto y del presupuesto; las cuatro etapas principales se muestran en una sola fila, sin marcas de verificación y con el color como indicador de avance. La barra fija reúne la acción principal y “Más acciones”; los títulos de “Detalle de ficha”, “Detalle de pedidos” y “Pagos”, sus tablas y el botón PDF mantienen la identidad azul y ocupan el ancho disponible. Los datos, acciones por estado y conexión con `/api/fichas/{id}` conservan el comportamiento de escritorio. <!-- Última modificación: 2026-10-26 -->
En la tabla de trabajos, descripción, estado y precio ocupan columnas diferenciadas tanto en escritorio como en móvil; las columnas de selección/eliminación se ajustan al estado de la ficha sin superponer datos. <!-- Última modificación: 2026-10-26 -->

## Operación y despliegue <!-- Última modificación: 2026-10-26 -->
El backend usa `AviantoBack/Dockerfile`; el servicio API expone internamente 8081, limita memoria a 2 GiB y procesos a 256 y depende del estado saludable de PostgreSQL. La JVM limita su heap al 50 % de la memoria disponible para dejar margen a memoria nativa. <!-- Última modificación: 2026-11-18 -->
Flyway V37 habilita la extensión PostgreSQL `unaccent` para los filtros de texto; no modifica tablas ni datos existentes. <!-- Última modificación: 2026-11-13 -->
Flyway V39 concede `clientes.completar_datos` a los roles existentes y agrega a `ficha_trabajo` la moneda, los importes de origen, la referencia de cotización y su fecha; las filas anteriores se inicializan como ARS con los importes ya guardados. El despliegue necesita salida HTTPS desde la API a `dolarapi.com` para consultar cotizaciones; si falla, la edición y creación de presupuestos ARS continúan disponibles. <!-- Última modificación: 2026-11-18 -->
Los servicios Docker Compose del backend ejecutan la API con `init: true`, para recolectar procesos hijos terminados. El healthcheck usa `CMD` directo a `wget` con timeout de 3 segundos y revisa `/actuator/health/readiness` cada 20 segundos con un límite de 5 segundos; evita una shell intermedia y procesos huérfanos. Nginx local envía Actuator y Springdoc al backend y conserva las reglas de acceso de Spring Security. <!-- Última modificación: 2026-10-26 -->
En la pila local, usar `docker compose --env-file .env -f docker-compose.yml up -d --build`; para frontend, backend, PostgreSQL y proxy, usar `docker compose --env-file .env -f docker-compose.full.yml up --build` desde `AviantoBack`. <!-- Última modificación: 2026-10-26 -->
En producción, el Compose está en `/opt/infra/stacks/avianto.compose.yml` y Caddy en `/opt/infra/edge/Caddyfile`; su bloque versionado en el repositorio backend es `ops/avianto.caddy`. Validar Compose y Caddy antes de reconstruir únicamente `avianto-api`. El Caddyfile global de producción usa `admin off`, por lo que los cambios no admiten recarga en caliente: requieren reiniciar `edge-caddy`, un proxy compartido que puede interrumpir brevemente los demás dominios alojados en el VPS. <!-- Última modificación: 2026-10-26 -->
Después de desplegar, confirmar salud de `avianto-api` y `avianto-postgres`; que `/actuator/health/readiness` y `/actuator/health/liveness` devuelvan JSON `UP`; que `/v3/api-docs` y `/v3/api-docs/swagger-config` devuelvan OpenAPI para Administración y `403` para Operario y anónimos; que el documento anuncie el host y esquema HTTPS recibidos por el proxy; que el inicializador Swagger adjunte el JWT solo a recursos del mismo origen; y que rutas API desconocidas devuelvan `404`. <!-- Última modificación: 2026-10-26 -->
La migración V39 modifica el esquema PostgreSQL de forma aditiva y conserva los importes existentes como ARS. Las rutas públicas del proxy no cambian; los permisos se aplican en el backend además de condicionar la visibilidad de las acciones en frontend. <!-- Última modificación: 2026-11-18 -->
El catálogo público AviantoVentas se sirve en `https://aviantomotos.neticar.com.ar/` desde `avianto-ventas-web:80`, detrás de Caddy y la red Docker `edge`; su publicación es independiente de la API operativa y no expone puertos del contenedor al host. <!-- Última modificación: 2026-11-18 -->
Las referencias CSS y JavaScript llevan `?v=<release>` para evitar que Cloudflare mezcle el HTML actualizado con recursos antiguos; Nginx exige revalidación de CSS/JS. Hay que cambiar `v` en cada release de frontend. <!-- Última modificación: 2026-11-18 -->
